AWS PrivateLinkを利用した
Amazon Bedrock VPCエンドポイント構成

生成AIサービスへのプライベート接続を「ホテルの社内専用通路」に例えて、豊富な図解で完全解説。bedrock-mantleエンドポイント（2026年2月GA）にも対応。

📌 結論ファースト：押さえるべき3つのポイント

1. PrivateLinkで「裏口専用通路」を作る
VPCインターフェイスエンドポイントを作成すると、インターネット非経由でAmazon Bedrockへプライベート接続できる。パブリックIPは不要。
2. 5種類のエンドポイントを使い分ける
bedrock / bedrock-runtime / bedrock-agent / bedrock-agent-runtime / bedrock-mantle（OpenAI互換・NEW）の5種類。
3. エンドポイントポリシーで最小権限
VPCエンドポイントにIAMポリシーをアタッチし、InvokeModel等の必要なアクションだけに絞ってデータ境界を実現。

🏨 たとえ話で理解する：ホテルの「社内専用通路」

💡 大型リゾートホテルに例えてみよう

あなたは大型リゾートホテル（VPC）の運営責任者です。ホテル内のレストランから別棟のシェフの厨房（Amazon Bedrock）に料理を注文したいとします。通常は正面玄関から一般道路（インターネット）を通りますが、セキュリティのために社内専用通路（PrivateLink）を設置しました。通路には専用受付窓口（VPCエンドポイント）があり、入館許可証（エンドポイントポリシー）でリクエストを制御します。

🏗 全体構成図：PrivateLinkによるBedrock接続

VPCのプライベートサブネット内からAWS PrivateLinkを経由してAmazon Bedrockに接続する全体構成を示します。

💡 図の読み方：① アプリがリクエスト送信 → ② ENI（専用受付窓口）で受付 → ③ PrivateLink経由でBedrock APIに到達。すべてAWSネットワーク内で完結。5種類のエンドポイントは用途別に選択。

🔗 接続パターン4選：段階的に図で理解する

PoC→本番まで段階的にセキュリティを高める4パターンを、それぞれ専用の図解で紹介します。

1パブリック接続（PoC向け・最もシンプル）
Lambda/パブリックサブネットのEC2からパブリック接続でBedrockを呼び出す最もシンプルな構成。
2プライベートAPIとの連携（VPC Lambda経由）
アクショングループにVPCアクセス許可Lambdaを設定し、プライベートサブネット内のEC2 APIと連携。エージェント呼出はパブリック。
3完全プライベート接続（本番推奨）
パターン2に加え、Agents Client→Bedrockの呼出もPrivateLink経由に。NAT Gateway不要。boto3のendpoint_urlにDNS名指定。
応リターンコントロール方式（Lambda不要・応用編）
アクショングループにリターンコントロールを設定。Client側から直接プライベートAPIを呼出。Lambda不要でオーバーヘッド削減。

🛡 セキュリティ3層防御の図解

VPCエンドポイント経由のBedrockアクセスは、3つのセキュリティレイヤーでデータ境界を構築します。

⚠ 重要：3つのレイヤーすべてで「Allow」されていないとアクセスできません。最小権限の原則に基づき、各層で必要最低限のアクセスのみ許可してください。

💻 セットアップ手順：コード例

# bedrock-runtime 用 VPCエンドポイント作成
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123def456 \
  --service-name com.amazonaws.ap-northeast-1.bedrock-runtime \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-0aaa111 subnet-0bbb222 \
  --security-group-ids sg-0ccc333 \
  --private-dns-enabled

# bedrock-mantle 用（OpenAI互換API）
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123def456 \
  --service-name com.amazonaws.ap-northeast-1.bedrock-mantle \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-0aaa111 subnet-0bbb222 \
  --security-group-ids sg-0ccc333 \
  --private-dns-enabled

# エンドポイントポリシー設定（最小権限）
aws ec2 modify-vpc-endpoint \
  --vpc-endpoint-id vpce-0ddd444 \
  --policy-document '{
    "Version":"2012-10-17",
    "Statement":[{
      "Principal":"*","Effect":"Allow",
      "Action":["bedrock:InvokeModel","bedrock:InvokeModelWithResponseStream"],
      "Resource":"*"
    }]
  }'
AWSTemplateFormatVersion: '2010-09-09'
Resources:
  BedrockEndpointSG:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Allow HTTPS for Bedrock VPC Endpoint
      VpcId: !Ref VpcId
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 443
          ToPort: 443
          CidrIp: !Ref VpcCidr

  BedrockRuntimeEndpoint:
    Type: AWS::EC2::VPCEndpoint
    Properties:
      VpcId: !Ref VpcId
      ServiceName: !Sub com.amazonaws.${AWS::Region}.bedrock-runtime
      VpcEndpointType: Interface
      SubnetIds: !Ref SubnetIds
      SecurityGroupIds: [!Ref BedrockEndpointSG]
      PrivateDnsEnabled: true
      PolicyDocument:
        Version: '2012-10-17'
        Statement:
          - Effect: Allow
            Principal: '*'
            Action:
              - bedrock:InvokeModel
              - bedrock:InvokeModelWithResponseStream
            Resource: '*'
resource "aws_security_group" "bedrock_vpce" {
  name_prefix = "bedrock-vpce-"
  vpc_id      = var.vpc_id
  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = [var.vpc_cidr]
  }
}

resource "aws_vpc_endpoint" "bedrock_runtime" {
  vpc_id              = var.vpc_id
  service_name        = "com.amazonaws.${var.region}.bedrock-runtime"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = var.subnet_ids
  security_group_ids  = [aws_security_group.bedrock_vpce.id]
  private_dns_enabled = true
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow", Principal = "*",
      Action = ["bedrock:InvokeModel","bedrock:InvokeModelWithResponseStream"],
      Resource = "*"
    }]
  })
}
import boto3, json

# パターン3: PrivateLink経由（プライベートDNS有効ならコード変更不要）
client = boto3.client("bedrock-runtime", region_name="ap-northeast-1")

response = client.invoke_model(
    modelId="anthropic.claude-sonnet-4-20250514",
    contentType="application/json",
    accept="application/json",
    body=json.dumps({
        "anthropic_version": "bedrock-2023-05-31",
        "max_tokens": 1024,
        "messages": [{"role": "user", "content": "AWSとは？"}]
    })
)
print(json.loads(response["body"].read())["content"][0]["text"])

# エージェント呼び出し（PrivateLink経由）
agent_client = boto3.client("bedrock-agent-runtime", region_name="ap-northeast-1")
response = agent_client.invoke_agent(
    agentId="AGENT_ID", agentAliasId="ALIAS_ID",
    sessionId="session-123", inputText="売上レポートを作成してください"
)

✅ ベストプラクティス vs ❌ アンチパターン

✅ ベストプラクティス
エンドポイントポリシーで最小権限の原則を適用
SGでHTTPS(443)のみ許可、ソースをVPC CIDRに制限
プライベートDNSを有効化してコード変更不要でPrivateLink化
必要なエンドポイントだけ作成しコスト最適化
複数AZサブネットに配置して高可用性確保
❌ アンチパターン
エンドポイントポリシーをデフォルト全許可のまま放置
SGで0.0.0.0/0を許可し意図しないアクセスを許す
プライベートDNS無効のままendpoint_url指定を忘れパブリック経由で通信
不要なエンドポイント（control plane等）まで作成し無駄なコスト
全アクショングループをリターンコントロールに寄せてClient肥大化

🔧 トラブルシューティング

⚠ 「endpoint does not support the Availability Zone」エラー
原因：指定サブネットのAZがBedrockエンドポイント未対応
✅ describe-vpc-endpoint-services で対応AZ確認→対応AZサブネットを選択
⚠ PrivateLink経由でBedrockを呼ぶとタイムアウト
原因：SGでHTTPS(443)未許可、またはルートテーブル問題
✅ エンドポイントSGでInbound 443許可。VPC DNS設定を有効に
⚠ プライベートDNS有効化後も名前解決できない
原因：VPCのDNS解決/DNSホスト名設定が無効
✅ VPC設定で「DNS解決」「DNSホスト名」両方を有効化
⚠ 「AccessDeniedException」が発生
原因：エンドポイントポリシーとIAMポリシー両方で許可が必要
✅ エンドポイントポリシーのActionにAPIアクション追加+IAMロール確認

📝 試験対策のポイント

🎯 ANS-C01 / SAP-C02 頻出ポイント

ANS-C01PrivateLinkとVPNの違い：PrivateLink=AWSサービスへのプライベート接続。VPN=オンプレミスとVPC接続。「インターネット非経由でAWSサービスにアクセス」→PrivateLink。
ANS-C01Interface vs Gateway EP：S3/DynamoDB以外はInterface（PrivateLink）。BedrockはInterface型。
SAP-C02データ境界：VPCエンドポイントポリシー+IAMポリシー+リソースポリシーの3層。「最も安全に生成AI利用」→PrivateLink。
SAP-C02コスト比較：NAT GW($0.062/GB) vs PrivateLink($0.01/GB)。「コスト最適化+セキュリティ」→PrivateLink。
ANS-C01プライベートDNS：有効にすると既存SDKコード変更不要。VPCのDNS設定が前提条件。

bedrock-runtimeは従来のBedrock推論API用。bedrock-mantleは2026年2月GA、Project Mantleによる高性能推論とOpenAI API互換を提供。新規プロジェクトではbedrock-mantle推奨。
AZ毎に約$0.014/時間 + $0.01/GB。NAT GW($0.062/時間+$0.062/GB)より大幅に安く、セキュリティも向上。

基本はLambdaを推奨（Client実装がシンプル）。リターンコントロールはLambdaのオーバーヘッド問題、15分制約超え、パブリック接続不可のセキュリティポリシー時に検討。

📖 用語集

AWS PrivateLink
AWSプライベートネットワーク内でVPCとサービス間のプライベート接続を確立。インターネット非経由。
インターフェイスエンドポイント
PrivateLinkを利用したVPCエンドポイント。サブネット内にENIが作成されトラフィックのエントリポイントに。
エンドポイントポリシー
VPCエンドポイントにアタッチするIAMリソースベースポリシー。許可するアクション・リソースを制御。
プライベートDNS
有効化するとサービスの標準DNS名がエンドポイントに解決。コード変更不要でPrivateLink化可能。
データ境界（Data Perimeter）
エンドポイントポリシー、IAMポリシー、リソースポリシーを組み合わせてデータアクセスの境界を定義。
Project Mantle
Bedrockの分散推論エンジン。高性能サーバーレス推論、自動容量管理、OpenAI API互換を提供。
リターンコントロール
Bedrockエージェントのアクショングループ設定。Lambdaを使わずClient側にAPI実行を委譲する方式。
VPC Lambda
VPCリソースへのアクセスを許可したLambda関数。ENIを通じてプライベートサブネット内に接続可能。
