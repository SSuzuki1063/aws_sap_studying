📘 AWS Black Belt シリーズ準拠

💡 結論ファースト：Transit Gateway とは

🎯 一言で言うと

複数のVPCとオンプレミスを一箇所で集中管理する「ネットワークのハブ空港」。VPC Peeringの複雑な接続管理から解放されます。

🔢 導入タイミング

VPCが3つ以上あり増加見込み、Direct Connect接続VPCが20超、通信監査・ガバナンスが必要な場合

⚡ 主要機能

VPC/VPN/Direct Connect接続、複数ルートテーブル、リージョン間ピアリング、マルチキャスト対応

📊 帯域幅

VPCアタッチメント: 最大100Gbps/AZ、MTU: 8500バイト のジャンボフレーム対応

📚 4つのコアコンセプトを理解する

🔗

Attachment（アタッチメント）

空港の「搭乗ゲート」

VPC、VPN、Direct Connect、他のTGWなどをTransit Gatewayに接続する「入口」です。各接続先ごとに1つのアタッチメントを作成します。

💡 重要：VPCアタッチメントは各AZにサブネット(/28以上)が必要。ENIがサブネット内に作成されます。

🗺️

Route Table（ルートテーブル）

空港の「フライト案内板」

パケットをどのアタッチメントに転送するか決める経路情報です。Transit Gatewayは複数のルートテーブルを持てるため、環境分離が可能です。

💡 重要：最低1つのルートテーブルが必要。デフォルトで1つ作成され、最大20個まで作成可能（上限緩和可）

🎫

Association（アソシエーション）

「搭乗券とゲートの紐付け」

アタッチメントとルートテーブルを紐付けます。VPCからTGWに入ったパケットは、アソシエートされたルートテーブルを参照して転送先を決定します。

💡 重要：1つのアタッチメントは1つのルートテーブルにしかアソシエートできません（1対1）

📢

Propagation（プロパゲーション）

「新規就航便の案内板への自動登録」

アタッチメントのCIDR情報をルートテーブルに自動伝播します。手動でスタティックルートを書く代わりに、動的に経路を登録できます。

💡 重要：プロパゲーションは複数のルートテーブルに設定可能。アソシエーションとは独立した設定です。

🔌 アタッチメントの種類

🏢

VPC Attachment

同一リージョン内のVPCを接続。最も基本的なアタッチメント。

  • ✅ 帯域: 最大100Gbps/AZ
  • ✅ MTU: 8500バイト対応
  • ✅ IPv4/IPv6サポート
  • ⚠️ 各AZにサブネット必要
🔒

VPN Attachment

Site-to-Site VPNでオンプレミスと暗号化接続。

  • ✅ 帯域: 最大1.25Gbps/トンネル
  • ✅ ECMPで帯域集約可能
  • ✅ BGPまたは静的ルート
  • ⚠️ Private IP VPNも対応
📡

Direct Connect Gateway

Transit VIF経由でDirect Connect Gatewayと接続。

  • ✅ 専用線で安定した接続
  • ✅ 複数VPCを1本のDXで接続
  • ✅ BGPによる動的ルーティング
  • ⚠️ Private VIFとの併用不可
🌍

Peering Attachment

他のTransit Gatewayとピアリング接続。

  • ✅ リージョン間接続対応
  • ✅ 同一リージョン内も可能
  • ⚠️ スタティックルートのみ
  • ⚠️ 双方でアクセプト必要
🔀

Connect Attachment

SD-WANアプライアンスとGRE/BGPで接続。

  • ✅ 帯域: 最大5Gbps/GREトンネル
  • ✅ VPCまたはDXGWがトランスポート
  • ✅ ECMPサポート
  • ⚠️ BGP over GREが必須

📊 ルート評価の優先順位（Best Path Selection）

Most Specific Route 最もプレフィックスが長い（詳細な）ルートが優先
Static Routes 手動設定のスタティックルート（Site-to-Site VPN含む）
Prefix List Referenced Routes プレフィックスリストを参照するルート
VPC Propagated Routes VPCアタッチメントからの伝播ルート
Direct Connect Gateway Routes DXGWからの伝播ルート
Transit Gateway Connect Routes Connectアタッチメントからの伝播ルート
Site-to-Site VPN Routes VPN接続からの伝播ルート

💼 代表的なユースケース

🏢 Shared VPC 構成

共通サービス（AD、DNS、Endpointなど）を置いたShared VPCを全VPCからアクセス可能にしつつ、ワークロードVPC間は分離する構成です。

📌 シナリオ例

本番VPC・開発VPC・テストVPCはお互いに通信させたくないが、監視や認証のためのShared VPCには全員がアクセスできるようにしたい。

🌐 ハイブリッドクラウド

オンプレミスデータセンターとAWS環境をVPN/Direct Connectで接続し、すべてのVPCとオンプレ間の通信をTGWで集約管理します。

📌 シナリオ例

既存のオンプレミス基盤を維持しながら、新規サービスをAWSで展開。両環境間のセキュアな通信とルーティング一元管理を実現。

🌍 グローバル展開

複数リージョンにまたがるワークロードをTGWピアリングで接続。AWSのグローバルバックボーンを活用した低遅延なリージョン間通信を実現。

📌 シナリオ例

東京リージョンのアプリケーションから、シンガポール・オレゴンリージョンのデータベースレプリカにアクセス。災害対策とグローバルサービス展開を両立。

📏 主要なクォータ（制限）

項目 デフォルト値 上限緩和 備考
アカウントあたりのTGW数 5 可能 リージョンごと
TGWあたりのルートテーブル数 20 可能 環境分離に影響
TGWあたりの経路数 10,000 可能 全ルートテーブル合計

✅ ベストプラクティス

✅ 推奨事項（Do）

  • ✓ 各AZにアタッチメント用サブネットを配置し、可用性を確保する
  • ✓ ルートテーブルを用途・環境ごとに分割し、セキュリティ境界を明確にする
  • ✓ Propagationを活用して動的にルートを管理し、運用負荷を軽減する
  • ✓ VPC Flow Logsと合わせてトラフィックを可視化・監査する
  • ✓ TGWのAZごとの帯域上限を考慮した設計をする
  • ✓ ECMP対応環境ではVPN接続を複数束ねて帯域を確保する

❌ アンチパターン（Don't）

  • ✗ VPC数が少ない（2つ以下）のにTGWを使用する → VPC Peeringで十分
  • ✗ 単一AZにのみアタッチメントを作成する → 可用性リスク
  • ✗ Transit VIFとPrivate VIFを同じDXGWで併用しようとする → 不可
  • ✗ ピアリング接続でBGPによる動的ルーティングを期待する → スタティックのみ
  • ✗ VPCサブネットのルートテーブルでTGW向けのルートを設定し忘れる
  • ✗ マルチキャストを後から有効化しようとする → TGW作成時のみ

❓ よくある質問（FAQ）

Q: VPC PeeringとTransit Gatewayの違いは？

VPC Peeringは2つのVPC間の1対1接続で、接続数が増えるとフルメッシュ構成が必要になり管理が複雑化します。Transit Gatewayはハブ＆スポーク型で、VPCが増えても管理がシンプルです。VPCが3つ以上ならTGWを検討しましょう。

Q: TGWの料金体系は？

アタッチメント時間（$/hour）とデータ処理量（$/GB）の2軸で課金されます。VPC Peeringより割高ですが、管理コストの削減や機能面でのメリットとのトレードオフを検討しましょう。

Q: 別アカウントのVPCも接続できる？

はい。Resource Access Manager（RAM）を使ってTGWを他のAWSアカウントと共有できます。AWS Organizationsと連携すれば、組織内でのマルチアカウント構成が容易になります。

Q: セキュリティグループは適用される？

TGW自体にセキュリティグループは適用できません。TGW通過後の通信制御は、各VPC内のセキュリティグループやNACL、またはNetwork Firewallで行います。

Q: Cloud WANとの違いは？

Transit Gatewayはリージョン単位で管理（Customer Managed）、Cloud WANはグローバルレベルで一元管理（AWS Managed）です。Cloud WANはBGPベースのリージョン間接続、Intent-basedポリシーなど高度な機能がありますが、TGWは柔軟なDIY設計が可能です。

Q: マルチキャストはどう使う？

TGW作成時にマルチキャストを有効化すると、TGWがマルチキャストルーターとして動作します。IGMPv2をサポートし、VPCアタッチメントのみで利用可能です。後から有効化はできないので注意。
