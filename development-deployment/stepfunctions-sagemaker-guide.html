🎯 まず結論：なぜ Step Functions × SageMaker AI なのか？

機械学習パイプラインを「人手」ではなく「ステートマシン」に任せる
CONCLUSION

Step Functions は SageMaker AI の4種類のジョブ（Training / Transform / Processing / Labeling）を JSON 定義のワークフローとして一筆書きでつなぎ、 .sync 統合パターンで「ジョブの完了を待って次へ」を自動化します。 これにより「データ準備 → 学習 → モデル作成 → エンドポイント公開」という MLOps の定型手順を、ポーリング用の Lambda を書かずに実装できます。

🔥
手動運用からの解放
コード更新→学習→デプロイを人手で回すと手順ミスが起きる。ワークフロー化で再現性を担保。
💰
遷移ごとの課金で低コスト
Step Functions は状態遷移の回数に応じた課金。待機中に料金が膨らまず、長時間ジョブに最適。
🛠
リトライ・エラー処理が組込み
Retry / Catch を宣言的に書けるので、ResourceLimitExceeded などに自動再試行。

🍳 たとえ話：レストラン厨房の指揮系統

総料理長（Step Functions）が4人の専門シェフ（SageMaker ジョブ）を動かす

あなたが大きなレストランの総料理長だとします。厨房には 食材仕分け担当、下ごしらえ担当、 メイン調理担当、大量盛り付け担当の4人の専門シェフがいます。 一人で全員に同時に指示を出すと必ず漏れが発生しますが、 「順番を書いたオーダーメモ」を作って従業員に渡し、各工程の完了を待ってから次の工程に進ませれば、あなたは他の業務に集中できます。 このオーダーメモの仕組みが、まさに Step Functions ステートマシンなのです。

図1: 総料理長（Step Functions）が4人の専門シェフ（SageMaker AI ジョブ）を順序立てて指揮する様子

なぜ「総料理長」が必要なのか？

シェフたちは自分の料理だけに集中します。食材仕分け担当は 「メイン調理が終わったか」を知りません。下ごしらえ担当も 「盛り付けがいつ始まるか」を気にしません。 工程全体の順番を管理する「責任者」がいないと、結局誰かが手動で各工程の完了を確認して、次のシェフに声をかける必要があります。 この「声かけ役」を自動化するのが Step Functions の役割です。

📦 4種類の SageMaker AI ジョブを使い分ける

Step Functions から呼び出せる .sync 対応ジョブの責務と使いどころ

Step Functions の最適化された SageMaker AI 統合では、以下の4つのジョブAPIが .sync 統合パターン（ジョブ完了まで待機）に対応しています。 それぞれ「何を」「何のために」行うかが明確に分かれており、 レストランの4人のシェフのように役割が重ならないのが特徴です。

🍫
CreateLabelingJob
生データに「正解」を付ける。人間の作業者や機械学習で自動ラベリングする教師データ作成ジョブ。

🍒
CreateProcessingJob
特徴量エンジニアリング、データクレンジング、モデル評価など学習前後の前処理／後処理を実行。
下ごしらえ
🍳
CreateTrainingJob
アルゴリズムとハイパーパラメータに基づいてモデルを学習。成果物は S3 に保存されるモデル重み。
メイン調理
🍱
CreateTransformJob
学習済モデルで大量データに対してバッチ推論を実行。リアルタイム API が不要な場面で使う。
大量盛り付け

補助的に使える API（.sync 非対応の即時完了系）

以下の API は瞬時に完了するためポーリング待機が不要で、リクエスト／レスポンス統合パターンで使用します。 モデル公開やエンドポイント設定で欠かせない登場人物たちです。

🍴
CreateModel

📝

🏩
CreateEndpoint
設定に基づいて実際に推論API（HTTPSカウンター窓口）を開業する。
🔃

営業中のカウンターで「新レシピに差し替える」。本番モデル更新に使う。

.sync 対応の分岐ジョブも1つある

IMPORTANT

CreateHyperParameterTuningJob（ハイパーパラメータ調整ジョブ）も .sync 統合パターンに対応しています。これは「複数のレシピを同時に試作して最も美味しい配合を選ぶ」ような仕事で、 内部的に多数のトレーニングジョブを実行します。

🔄 3つの統合パターンと SageMaker AI の対応

Step Functions が外部サービスを呼び出す際の「待ち方」の選択肢

Step Functions には外部 AWS サービスを呼び出す際の3つの統合パターンがあります。 SageMaker AI では .sync と Request-Response は使えるが .waitForTaskToken は使えない点が重要です。

推奨
✅ ジョブの実行（.sync）
「ジョブが終わるまで待って、完了したら次へ」。Step Functions が裏で自動ポーリングして状態を監視します。
SageMaker 対応: Training / Transform / Processing / Labeling / HyperParameterTuning
即時完了向け
⚡ レスポンスのリクエスト
API を呼び出したら即レスポンスを受け取って次へ進む。短時間で終わる操作向け。
SageMaker 対応: CreateModel / CreateEndpointConfig / CreateEndpoint など
非対応
❌ タスクトークンのコールバック待ち
外部システムから明示的に完了通知が来るまで待つ。人間の承認など非同期処理用。
SageMaker 対応: 非対応（代わりに .sync を使う）
💡 ヒント
🎯 .sync が最適な理由
SageMaker ジョブは数分〜数日かかる長時間処理。Lambda の15分タイムアウトでは待てないため、.sync が設計上の必然です。
課金: 遷移回数ベース（待機中は無料）で1年間実行可能

パイプラインを支える AWS サービスの役割

📣
Amazon SNS
ビルド開始トリガーと完了通知のハブ。CodeCommit / S3 / EventBridge からトピックに発行される。
🔧
AWS CodeBuild
オンデマンドで Docker イメージをビルドして ECR にプッシュ。カスタムアルゴリズムの準備工程。
⚙️
AWS Lambda
ジョブ設定パラメータの動的生成、前工程の結果を次工程の入力に整形するグルー役。
🗃️
Parameter Store
インスタンスタイプや S3 バケット名などの設定を集中管理。JSON を書き換えるだけで設定変更可能。
📊
CloudWatch
各ジョブのログ・メトリクスを収集。トレーニング損失の推移などを可視化できる。
📡
EventBridge
「毎週金曜 21時に再学習」のような定期実行スケジュール。週末バッチに最適。

Amazon States Language（ASL）で記述するステートマシン定義の実例

🍳 1. トレーニングジョブ（CreateTrainingJob）

アルゴリズム、ハイパーパラメータ、インスタンス構成、入出力 S3 パスを指定してモデルを学習させる、最も重要なジョブです。 Retry / Catch でエラーハンドリングも組み込める点に注目してください。

📝 ASL 定義（ステートマシン定義 JSON）
"SageMaker CreateTrainingJob": {
  "Type": "Task",
  "Resource": "arn:aws:states:::sagemaker:createTrainingJob.sync",
  "Arguments": {
    "TrainingJobName": "search-model",
    "ResourceConfig": {
      "InstanceCount": 4,
      "InstanceType": "ml.c4.8xlarge",
      "VolumeSizeInGB": 20
    },
    "HyperParameters": {
      "mode": "batch_skipgram",
      "epochs": "5",
      "learning_rate": "0.025"
    },
    "AlgorithmSpecification": {
      "TrainingImage": "...",
      "TrainingInputMode": "File"
    },
    "OutputDataConfig": {
      "S3OutputPath": "s3://amzn-s3-demo-destination-bucket1/doc-search/model"
    },
    "StoppingCondition": { "MaxRuntimeInSeconds": 100000 },
    "RoleArn": "arn:aws:iam::account-id:role/docsearch-stepfunction-iam-role",
    "InputDataConfig": [ ... ]
  },
  // エラー時のリトライ戦略
  "Retry": [
    { "ErrorEquals": ["SageMaker.ResourceLimitExceededException"],
      "IntervalSeconds": 60,
      "MaxAttempts": 5000,
      "BackoffRate": 1 }
  ],
  "Catch": [
    { "ErrorEquals": ["States.ALL"], "Next": "Sagemaker Training Job Error" }
  ],
  "Next": "Delete Interim Data Job"
}

🚨 エラーハンドリング（Retry / Catch）

「シェフが倒れたら代役を立てる」指示も事前に書いておく

長時間のトレーニングジョブは、リソース制限・一時的な障害・サービスの例外で失敗することがあります。 Step Functions では各 Task ステートに Retry（自動再試行）と Catch（失敗時の分岐）を宣言的に書けます。

図7: Retry の繰り返し、その後に Catch でエラー処理に分岐する動作の全体像

典型的な Retry / Catch 設定

📝 Retry / Catch の実例
"Retry": [
  {
    "ErrorEquals": ["SageMaker.AmazonSageMakerException"],
    "IntervalSeconds": 1,
    "MaxAttempts": 100,
    "BackoffRate": 1.1        // 指数バックオフで徐々に待機時間を増やす
  },
  {
    "ErrorEquals": ["SageMaker.ResourceLimitExceededException"],
    "IntervalSeconds": 60,       // 60秒待ってから
    "MaxAttempts": 5000,       // 最大5000回（= 他ジョブ終了を気長に待つ）
    "BackoffRate": 1            // 定間隔
  },
  {
    "ErrorEquals": ["States.Timeout"],
    "IntervalSeconds": 1,
    "MaxAttempts": 5,
    "BackoffRate": 1
  }
],
"Catch": [
  {
    "ErrorEquals": ["States.ALL"],        // 上記 Retry で救えなかった全エラー
    "Next": "Sagemaker Training Job Error"
  }
]

🔑 IAM ポリシー設計

シェフの資格証・名札を正しく発行する
注意

CreateTransformJob だけは、Step Functions がステートマシン作成時に IAM ポリシーを自動生成しません。 他のジョブは自動アタッチされますが、Transform は作成後に手動でインラインポリシーをアタッチする必要があります。

トレーニングジョブ用 IAM ポリシー（.sync 統合パターン／静的リソース）

以下は Run a Job (.sync) 統合パターン用の最小権限ポリシー例です。

📝 CreateTrainingJob の IAM ポリシー
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "sagemaker:CreateTrainingJob",      // 学習ジョブ開始
        "sagemaker:DescribeTrainingJob",   // .sync ポーリング用
        "sagemaker:StopTrainingJob"        // 実行停止用
      ],
      "Resource": ["arn:aws:sagemaker:us-east-1:123456789012:training-job/myJobName*"]
    },
    {
      "Effect": "Allow",
      "Action": ["sagemaker:ListTags", "sagemaker:AddTags"],
      "Resource": ["*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iam:PassRole"],  // SageMakerにロール委譲
      "Resource": ["arn:aws:iam::123456789012:role/MyExampleRole"],
      "Condition": {
        "StringEquals": { "iam:PassedToService": "sagemaker.amazonaws.com" }
      }
    },
    {
      "Effect": "Allow",
      "Action": [
        "events:PutTargets", "events:PutRule", "events:DescribeRule"
      ],
      "Resource": [
        "arn:aws:events:us-east-1:123456789012:rule/StepFunctionsGetEventsForSageMakerTrainingJobsRule"
      ]
    }
  ]
}

ポリシーを構成する4つの権限ブロック

🛠
SageMaker ジョブ操作権限
Create / Describe / Stop の3セットが必要。.sync の裏では Describe が定期的に呼ばれる。
🏷️
タグ管理権限
ListTags / AddTags で Step Functions がジョブに識別用タグを付けて追跡する。
🔗
iam:PassRole
SageMaker 実行用ロールを SageMaker サービスに渡す権限。Condition で渡し先を制限するのが鉄則。
📡
EventBridge 連携権限
.sync が使う内部ルール（StepFunctionsGetEventsForSageMakerXxxJobsRule）の作成権限。

🏆 ベストプラクティス

本番運用で差がつく8つの設計指針
1

常に .sync 統合を使う

Training/Transform/Processing/Labeling は長時間処理。Lambda で独自ポーリングを書くより、ビルトインの .sync が圧倒的に安定・低コスト。

2

Retry を必ず設定する

ResourceLimitExceeded（リソース枯渇）は一時的なので長めに再試行。AmazonSageMakerException も Backoff で緩やかに再試行。

3

Catch で失敗時の後始末を書く

States.ALL を catch して SNS 通知や S3 クリーンアップへ遷移。「失敗したまま放置」を避けるためのゲートを必ず設ける。

4

Parameter Store で設定を外出し

インスタンスタイプ、S3 パス、インスタンス数などはコードに埋め込まず Parameter Store から Lambda 経由で注入する。

5

CreateTransformJob の IAM は手動

自動生成されないため、必ずステートマシン作成後にインラインポリシーをアタッチする。漏れると実行時に AccessDenied。

6

iam:PassRole に Condition を付ける

iam:PassedToService を sagemaker.amazonaws.com に固定。他サービスへの権限漏洩を防ぐ最小権限原則の要。

7

静的リソース命名で Resource を狭める

training-job/myJobName* のようにプレフィックス固定にすることで、意図しないジョブへの権限拡散を防ぐ。

8

トレーニングに検証ロジックを組み込む

aws-sagemaker-build はトレーニング失敗以外では必ずデプロイする。精度低下モデルの自動公開を避けるため、Choice ステートで閾値判定を追加。

❓ よくある質問（FAQ）

Step Functions と SageMaker AI の統合でよく聞かれる質問をまとめました。

Q

Step Functions から SageMaker Endpoint を直接呼び出して推論できますか？

A

いいえ、SageMaker AI の最適化統合では InvokeEndpoint は提供されていません。リアルタイム推論は Lambda や API Gateway 経由で呼び出してください。Step Functions はモデルの「作成・学習・バッチ推論」のオーケストレーションに使います。

Q

.waitForTaskToken は使えますか？

A

いいえ、SageMaker AI の最適化統合では .waitForTaskToken はサポートされていません。ジョブ完了を待つには .sync を、待たない場合は Request-Response（無印）を使います。人間の承認を挟みたい場合は Lambda + SNS + TaskToken を別ステップで組むパターンが一般的です。

Q

CreateTrainingJob の IAM ポリシーは自動で作られるのに、なぜ CreateTransformJob は手動なのですか？

A

これは公式ドキュメントに明記された仕様です。Step Functions はステートマシン作成時に Training / Processing / Labeling / HyperParameterTuning の .sync 用 IAM は自動生成しますが、CreateTransformJob.sync だけは例外で手動アタッチが必要です。ANS-C01 / SAP-C02 の引っかけポイント。

Q

Standard ワークフローと Express ワークフローはどちらを使うべき？

A

SageMaker のジョブは通常数分〜数時間かかるため、Standard 一択です。Express は最大 5 分までで料金モデルも異なります（実行時間＋メモリ課金）。高頻度・短時間ワークフローには Express が向きますが、ML パイプラインでは不向きです。

Q

Step Functions から SageMaker Pipelines（SageMaker Model Building Pipelines）を呼び出せますか？

A

はい、sagemaker:startPipelineExecution / .sync が使えます。ただし、SageMaker Pipelines 自体が ML 特化のオーケストレーションツールのため、どちらを採用するかは組織の方針で決めるのが定石です。Step Functions は「SageMaker 以外の AWS サービスも混ぜたい」場面で優位です。

Q

ジョブの途中経過（進捗率）を取得するにはどうすればよいですか？

A

.sync 統合で DescribeTrainingJob 相当を自動ポーリングしているため、Step Functions 側の画面で開始・完了時刻は確認できます。より詳細な進捗（エポック数等）は CloudWatch Logs や CloudWatch Metrics を別途確認してください。

Q

ジョブ名（TrainingJobName 等）が衝突するとどうなりますか？

A

SageMaker はアカウント＋リージョン内でジョブ名一意制約があり、重複するとエラーになります。ASL の $$.Execution.Name（実行 ID）を Suffix にするか、States.Format で日時を付与するのが定石です。例："TrainingJobName.$": "States.Format('my-job-{}', $$.Execution.Name)"

Q

失敗したジョブだけ自動で再実行する仕組みはありますか？

A

Retry 句で ErrorEquals に SageMaker.AmazonSageMakerException や States.TaskFailed を指定し、IntervalSeconds / BackoffRate / MaxAttempts で制御します。スポットインスタンス起因の中断は MaxAttempts を 3〜5 に、課金ミスや設定ミス由来は再試行しない設計が推奨です。

Q

ハイパーパラメータチューニング（HPO）も Step Functions から実行できますか？

A

はい、sagemaker:createHyperParameterTuningJob / .sync が使えます。Warm Start や並列ジョブ数の指定も可能です。HPO 後に Best TrainingJob を CreateModel → Endpoint にデプロイする一連の流れをステートマシンで完結できます。

Q

コスト最適化のベストプラクティスを教えてください。

A

（1）Managed Spot Training で最大 90% 削減、（2）TrainingJob の MaxRuntimeInSeconds で暴走防止、（3）Endpoint は必要時のみ起動（バッチ推論で済むならエンドポイント不要）、（4）古いモデルアーティファクトの S3 Lifecycle による自動削除、（5）開発環境は smaller インスタンス（ml.t3 系）に統一、の 5 点が定石です。

🎯 まとめ：4 ステップで理解する Step Functions × SageMaker

最後に、このガイド全体を 4 ステップに凝縮します。ここだけでも押さえれば現場・試験で戦えます。

1
役割分担を理解
Step Functions は「総料理長（オーケストレーター）」、SageMaker は「専門シェフ（実行者）」。Step Functions 自体は ML を実行せず、SageMaker API を順番に叩くだけ。
2
.sync 統合を選ぶ
長時間ジョブ（Training / Transform / Processing / Labeling / HPO）はすべて .sync を付ける。完了まで待ってから次のステートへ進む。.waitForTaskToken は使えない。
3
IAM を正しく設定
CreateTransformJob.sync だけは自動ポリシー生成されないので手動アタッチ。他にも iam:PassRole（Condition 付き）、events:* を忘れずに。
4
Retry / Catch で堅牢化
スポット中断・一時的エラーは Retry、致命的エラーは Catch で分岐。コスト最適化は Managed Spot Training と MaxRuntimeInSeconds でほぼ完結。
