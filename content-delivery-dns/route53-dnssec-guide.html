Route 53 DNSSEC 完全ガイド

公証役場のしくみで理解する DNS セキュリティと DS レコード設定

🎯 この記事の結論（30秒で理解）

🔑

DNSSEC とは？

DNS応答が 本物であることを暗号署名で証明 する仕組み。なりすましや改ざんを防止します。

📜

DS レコードの役割

親ドメイン（上位機関）に登録する 「お墨付き」 。信頼の連鎖を構築する重要な鍵です。

⚙️

設定の流れ

① KSK作成 → ② 署名有効化 → ③ DS レコード登録 → ④ 信頼チェーン確立（ 約15〜30分 ）

⚠️

最重要注意点

DS レコード登録後、 TTL経過を待たずに無効化すると障害発生 。必ず順序を守ること！

🏛️ たとえ話で理解：公証役場のしくみ

DNSSEC は、インターネット上の 「公証制度」 です。
あなたのドメインが発行する情報に「これは本物ですよ」という お墨付き を与えます。

🏛️ 現実世界：公証役場

💡 つまりこういうこと！

あなたが「example.com」の DNS レコードを発行するとき、 DNSSEC はそのレコードに「公証印」を押します。

そして DS レコード は、親ドメイン（.com）に対して「example.com の印鑑は本物ですよ」と登録する手続きです。

これにより、世界中の DNS リゾルバが「このDNS情報は改ざんされていない」と確認できるようになります！

🌍

Root Zone（ルートゾーン）

インターネットの最上位。全ての信頼の源

⬇️ DS レコードで保証
🏢

TLD（.com, .jp など）

トップレベルドメインのゾーン

⬇️ DS レコードで保証
🏠

あなたのドメイン

example.com（Route 53 で管理）

⬇️ KSK/ZSK で署名
📋

DNS レコード

A, AAAA, CNAME, MX など全て署名済み

🔑 キーの種類を理解しよう

🗝️

ZSK（Zone Signing Key）

ゾーン署名鍵

役割： 実際の DNS レコード（A, CNAME 等）に署名します。

管理： Route 53 が 自動管理 するため、ユーザーの操作は不要です。

💡 公証人が書類に押す「日常使いの印鑑」のようなもの

🔐

KSK（Key Signing Key）

鍵署名鍵

役割： ZSK に署名し、DNSKEY レコードを作成します。

管理： AWS KMS の CMK と連携。 ユーザーが作成・ローテーション します。

💡 公証人の「実印」に相当。厳重に管理される

📜

DS レコード

Delegation Signer

役割： KSK の公開鍵のハッシュ値。親ゾーンに登録して信頼を委任します。

登録先： ドメインレジストラ（Route 53 または他社）経由で TLD に登録。

💡 公証役場への「印鑑登録証明書」

✍️

RRSIG レコード

Resource Record Signature

役割： 各 DNS レコードに付与される電子署名そのもの。

生成： DNSSEC 有効化後、Route 53 が 自動生成 します。

💡 書類に押された「署名」そのもの

📋 DNSSEC 有効化 & DS レコード設定手順

0

📊 事前準備（重要！）

障害発生時のロールバックを容易にするため、以下を実施します。

  • CloudWatch アラーム設定： DNSSECInternalFailure と DNSSECKeySigningKeysNeedingAction を監視
  • TTL を低くする： レコードの TTL を 3600 秒（1時間）以下に設定
  • SOA の TTL と Minimum を下げる： ネガティブキャッシュの影響を軽減
  • TLD が DNSSEC をサポートしているか確認
1

🔐 KSK（鍵署名鍵）の作成

Route 53 コンソールで、AWS KMS の CMK を使って KSK を作成します。

  • Route 53 コンソール → ホストゾーン → 対象ドメインを選択
  • 「DNSSEC signing」タブ → 「Enable DNSSEC signing」
  • 既存の KMS CMK を選択、または新規作成
  • KSK 名を入力して「Create KSK and enable signing」をクリック
2

✅ 署名の有効化確認

DNSSEC signing のステータスが「Signing」になっていることを確認します。

  • ステータスが「Signing」になるまで数分待機
  • KSK のステータスが「Active」であることを確認
  • dig コマンドで DNSKEY レコードが返されることを確認
3

📋 DS レコード情報の取得

親ゾーンに登録するための DS レコード情報を取得します。

  • 「DNSSEC signing」タブ → 「View information to create DS record」
  • レジストラの種類（Route 53 / 他社）を選択
  • Key type, Signing algorithm, Public key（または DS 値）をメモ
4

📝 DS レコードの登録

取得した情報を使って、ドメインレジストラ経由で親ゾーンに DS レコードを登録します。

  • Route 53 で登録の場合： 「Registered domains」→ 対象ドメイン → 「DNSSEC keys」→ 「Add key」
  • Key type（KSK or ZSK）を選択
  • Algorithm を選択（通常 ECDSAP256SHA256）
  • Public key を貼り付けて「Add」
  • 他社レジストラの場合： 各社の管理画面で DS レコードを追加
5

🔍 信頼チェーンの確認

DNS リゾルバが DNSSEC を正しく検証できることを確認します。

  • DS レコードが伝播するまで待機（数分〜数時間）
  • dig コマンドで DS レコードが返されることを確認
  • オンラインツール（DNSViz, Verisign Labs など）で検証
  • 2週間程度の監視期間を設けてから TTL を戻す

💻 AWS CLI コマンド例 

# 1. まず DNSSEC 用の KMS キーを作成（まだない場合）
aws kms create-key \
  --description "DNSSEC KSK for example.com" \
  --key-usage SIGN_VERIFY \
  --customer-master-key-spec ECC_NIST_P256 \
  --policy '{"Version":"2012-10-17","Statement":[{"Sid":"Route53","Effect":"Allow","Principal":{"Service":"dnssec-route53.amazonaws.com"},"Action":["kms:DescribeKey","kms:GetPublicKey","kms:Sign"],"Resource":"*"}]}'

# 2. KSK を作成
aws route53 create-key-signing-key \
  --hosted-zone-id Z1234567890ABC \
  --key-management-service-arn arn:aws:kms:ap-northeast-1:123456789012:key/your-key-id \
  --name "example-com-ksk" \
  --status ACTIVE
# DNSSEC 署名を有効化
aws route53 enable-hosted-zone-dnssec \
  --hosted-zone-id Z1234567890ABC

# ステータス確認
aws route53 get-dnssec \
  --hosted-zone-id Z1234567890ABC

# 出力例
# {
#   "Status": {
#     "ServeSignature": "SIGNING"
#   },
#   "KeySigningKeys": [...]
# }
# KSK 情報を取得（DS レコード作成に必要な情報を含む）
aws route53 get-dnssec \
  --hosted-zone-id Z1234567890ABC \
  --query 'KeySigningKeys[?Status==`ACTIVE`]'

# 出力される PublicKey と KeyTag を使用して DS レコードを登録
# DS レコードのフォーマット:
# [KeyTag] [Algorithm] [DigestType] [Digest]
# 例: 12345 13 2 49FD46E6C4B45C55D4AC...

# Route 53 でドメイン登録している場合の DS 追加
aws route53domains associate-delegation-signer-to-domain \
  --domain-name "example.com" \
  --signing-attributes \
    Algorithm=13,\
    Flags=257,\
    PublicKey="YOUR_PUBLIC_KEY_BASE64"
# DNSKEY レコードの確認
dig example.com DNSKEY +short

# DS レコードの確認（親ゾーンから）
dig example.com DS +short

# DNSSEC 署名付きで確認（+dnssec オプション）
dig example.com A +dnssec

# RRSIG（署名）が付いていることを確認
dig example.com A +dnssec +short

# 信頼チェーン全体を検証（delv コマンド使用）
delv example.com A +rtrace

# オンラインツールでの確認も推奨
# - https://dnsviz.net/
# - https://dnssec-analyzer.verisignlabs.com/

📝 検証の流れ

  1. リゾルバは Root Zone の公開鍵（トラストアンカー）を保持
  2. Root の DS レコードで .com の DNSKEY を検証
  3. .com の DS レコードで example.com の DNSKEY（KSK）を検証
  4. KSK で ZSK を検証
  5. ZSK で A レコードの RRSIG を検証
  6. すべて OK なら「このレコードは本物」と判定 ✅

⚠️ 絶対に守るべき注意事項

❌ 順序を間違えない

DNSSEC を 無効化する前に DS レコードを削除 する必要があります。 順序を間違えると、ドメインが インターネットからアクセス不能 になります。

無効化の順序：DS 削除 → TTL 待機（2日）→ DNSSEC 無効化

⏰ TTL 経過を待つ

DS レコード削除後、 TTL が経過するまで（通常2日） 待ってから次のステップに進みます。 キャッシュが残っている間に無効化すると、検証エラーが発生します。

🔑 KSK のローテーション

KSK は Route 53 が自動ローテーションしません。 セキュリティポリシーに従って 定期的に手動ローテーション を行う必要があります。

📊 TTL の制限

DNSSEC 有効化後、Route 53 は TTL を 最大1週間に制限 します。 それ以上の TTL を設定しても、1週間として扱われます。

🌐 マルチベンダー非対応

DNSSEC 署名を使用する場合、 複数の DNS プロバイダーの併用 はサポートされません。 すべてのネームサーバーは単一のプロバイダーから提供される必要があります。

📡 親ゾーンの DS 対応確認

親ゾーンが DS クエリを正しくサポートしていない場合、 子ゾーンで DNSSEC を有効にすると 名前解決できなくなる 可能性があります。

📊 レジストラ別 DS レコード登録方法

レジストラ 登録方法 入力項目 注意点
Route 53 Registered domains → DNSSEC keys → Add key Key type, Algorithm, Public key 最も簡単。コンソールで完結
お名前.com ドメイン設定 → DNSSEC 設定 Key Tag, Algorithm, Digest Type, Digest DS 形式での入力が必要
Cloudflare DNS 設定 → DNSSEC → Enable 自動生成される DS 値をコピー Cloudflare DNS 使用時は自動
GoDaddy DNS Management → DNSSEC Key Tag, Algorithm, Digest Type, Digest プレミアムプラン要の場合あり
ムームードメイン ドメイン管理 → DNSSEC Key Tag, Algorithm, Digest 対応 TLD が限られる場合あり

✨ ベストプラクティス

📉

有効化前に TTL を下げる

TTL を 300〜3600 秒に下げておくと、問題発生時のロールバックが速くなります。 正常動作を確認してから（2週間程度）元の値に戻します。

📊

CloudWatch アラームで監視

DNSSECInternalFailure と DNSSECKeySigningKeysNeedingAction メトリクスを監視し、 問題を早期検知できるようにします。

🔄

KSK ローテーション計画

セキュリティポリシーに従って KSK のローテーション計画を立て、 定期的に実施します。新しい KSK の DS を追加 → 古い DS を削除の順序を守ります。

🧪

テスト環境で検証

本番ドメインで有効化する前に、テスト用のサブドメインや別ドメインで DNSSEC の動作を確認することを推奨します。

📝

ドキュメント化

KMS キー ARN、KSK 名、有効化日時、DS レコード情報などを文書化し、 チームで共有します。障害対応時に必要になります。

❓ よくある質問（FAQ）

DNSSEC を有効にすると DNS クエリが遅くなりますか？ +

わずかに遅くなる可能性がありますが、通常は体感できないレベルです。 RRSIG などの追加レコードにより応答サイズが大きくなりますが、 キャッシュにより影響は最小限に抑えられます。 セキュリティ向上のメリットが、パフォーマンスへの影響を上回ります。

サブドメインにも DNSSEC を設定する必要がありますか？ +

親ドメインで DNSSEC を有効にすると、その親ホストゾーン内のすべてのレコードが署名されます。 ただし、別のホストゾーンで管理している委任されたサブドメインの場合は、 そのサブドメインのホストゾーンでも個別に DNSSEC を設定し、 親ゾーンに DS レコードを追加する必要があります。

DNSSEC の料金はかかりますか？ +

Route 53 での DNSSEC 署名自体には追加料金はかかりません。 ただし、KSK の管理に使用する AWS KMS の CMK には通常の KMS 料金（月額約 $1 + 使用量）がかかります。 また、署名により DNS 応答サイズが増加するため、クエリコストがわずかに増加する可能性があります。

DNSSEC を無効化する正しい手順は？ +

必ず以下の順序で実行します：

1. レジストラで DS レコードを削除
2. DS レコードの TTL が経過するまで待機（通常 48〜72 時間）
3. Route 53 コンソールで「Disable DNSSEC signing」を実行
4. KSK を非アクティブ化・削除

順序を間違えると、ドメインがインターネットから到達不能になります。

すべての TLD で DNSSEC を使用できますか？ +

いいえ、TLD によっては DNSSEC をサポートしていないものがあります。 主要な gTLD（.com, .net, .org など）や多くの ccTLD はサポートしていますが、 一部の新しい gTLD や特定の ccTLD では対応していない場合があります。 Route 53 のドキュメントで対応状況を確認してください。

Algorithm は何を選べばいいですか？ +

現在は ECDSAP256SHA256（Algorithm 13） が推奨されています。 RSA ベースの Algorithm 8 より鍵が小さく、パフォーマンスが良好です。 Route 53 のデフォルトも ECDSAP256SHA256 です。 古い RSA アルゴリズム（Algorithm 5, 7）はセキュリティ上の理由から非推奨です。
