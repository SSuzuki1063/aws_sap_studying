🔐 SAML証明書ローテーション完全ガイド

IAM IDプロバイダー設定更新の正しい手順と恒久対策

🏢 会社の入館証システムで例えると超わかりやすい！

SAMLフェデレーション = 外部の身分証明書で会社に入るシステム

社員証（AWS IAMユーザー）を持っていなくても、
信頼された外部機関が発行した身分証明書 で入館できる仕組みです。

でも、その信頼の証である 「署名証明書」には有効期限 があります。
期限切れになる前に、 正しい順番で 更新しないと...😱
全員が会社に入れなくなってしまいます！

🎭 入館証システムで理解するSAML認証

🏛️

Identity Provider（IdP）
= 身分証明発行機関

🎯 例えるなら：
市役所や運転免許センターのような 「公的な身分証明書を発行する機関」
📝 実際の役割：
• Okta、Azure AD、Google Workspaceなど
• ユーザーの認証を行う
• 「この人は本人ですよ」という証明書（SAMLアサーション）を発行
• 署名証明書で「偽造防止のハンコ」を押す
🔏 署名証明書の役割：
市役所の公印のようなもの。
「この証明書は確かにうちが発行しました」という証拠
🏢

Service Provider（SP）
= 入館を許可する会社

🎯 例えるなら：
あなたが入りたい 「会社のビル」 （AWS）
📝 実際の役割：
• AWS = Service Provider
• IAM IDプロバイダー = 「信頼する発行機関のリスト」
• 提示された証明書が本物か確認
• 登録された公印（証明書）と照合
🔑 IAM IDプロバイダーの役割：
警備室に掲示された「信頼できる発行機関一覧」と「その公印サンプル」
ここに登録されていないと入れない！

🔄 SAML認証の流れ（入館の流れ）

👤

ユーザー

「AWSにログインしたい」

➡️
🏛️

IdP（Oktaなど）

「この人は本人です」
署名証明書で署名

➡️
🏢

AWS（IAM）

「署名を確認...OK！」
アクセス許可

📚 3つの重要な登場人物

📜

署名証明書
（Signing Certificate）

何をするもの？
IdPが発行するSAMLアサーション（「この人は本人です」という証明）に 電子署名 を付けるための鍵

例えるなら：
市役所の公印。これがないと証明書は偽物扱いされる

有効期限：
通常1〜3年。期限切れ＝公印が無効になる
📋

メタデータ
（Metadata XML）

何をするもの？
IdPの情報をまとめた設定ファイル。署名証明書も含まれる

例えるなら：
「この発行機関の情報一式」
• 機関名
• 所在地（エンドポイントURL）
• 公印サンプル（証明書）

形式：
XML形式のファイル
🔗

IAM IDプロバイダー
（Identity Provider）

何をするもの？
AWSが「このIdPを信頼する」という設定。メタデータを登録する場所

例えるなら：
会社の警備室にある「信頼できる発行機関リスト」

重要ポイント：
ここに登録された証明書と、持ってきた証明書の署名が一致しないと入れない！

❌ やってはいけない！間違った更新手順

1️⃣
IdPで古い証明書を削除
「新しいのに変えるから古いのは消そう」
➡️
2️⃣
IdPで新しい証明書を設定
「よし、新しい証明書で署名するぞ」
➡️
3️⃣
AWSのIAM IDプロバイダーを更新
「あ、AWS側も更新しなきゃ」

💀 結果：全ユーザーがログインできなくなる！

ステップ1と2の間で 「署名と登録証明書が一致しない」状態 が発生！
IdPは新しい証明書で署名 → AWSは古い証明書しか知らない → 認証失敗 😱

✅ 正しい証明書ローテーション手順

📝
STEP 1
IdPで新しい証明書を「追加」する
古い証明書は 削除せずに残したまま 、新しい証明書を追加します。
この時点では、まだ古い証明書で署名を続けます。
🏛️ 例え：
市役所「新しい公印を作りました。でも古い公印もまだ使えます」
📥
STEP 2
IdPから新しいメタデータをダウンロード
新しい証明書を含むメタデータXMLをエクスポートします。
このメタデータには 新旧両方の証明書 が含まれています。
🏛️ 例え：
市役所「新旧両方の公印サンプルが載った資料をお渡しします」
☁️
STEP 3
AWS IAM IDプロバイダーを更新
新しいメタデータをAWSにアップロードします。
これでAWSは 新旧両方の証明書 を認識できるようになります。
🏢 例え：
会社「警備室のリストを更新！新旧両方の公印を受け入れます」
🔄
STEP 4
IdPで新しい証明書を「有効化」
IdP側で、署名に使う証明書を新しいものに切り替えます。
AWSは新しい証明書を知っているので、認証は成功します！
🏛️ 例え：
市役所「これからは新しい公印で署名します」→ 会社も受け入れOK！
✅
STEP 5
動作確認
実際にSAML認証でAWSにログインできるか確認します。
複数のユーザーで、複数のロールへのアクセスをテストしましょう。
✓ 確認項目：
• 通常ユーザーのログイン
• 管理者ユーザーのログイン
• 各IAMロールへのAssumeRole
🗑️
STEP 6
古い証明書を削除（オプション）
動作確認が完了し、問題がなければ古い証明書を削除します。
数日〜1週間は残しておく ことを推奨します。
⚠️ 注意：
すぐに削除せず、しばらく様子を見てから削除する方が安全
📝 AWS CLI / CloudFormation でのIAM IDプロバイダー更新 
# AWS CLI でメタデータを更新する
aws iam update-saml-provider \
    --saml-provider-arn "arn:aws:iam::123456789012:saml-provider/MyIdP" \
    --saml-metadata-document file://new-metadata.xml

# メタデータの内容を確認する
aws iam get-saml-provider \
    --saml-provider-arn "arn:aws:iam::123456789012:saml-provider/MyIdP"

# CloudFormation での定義例
Resources:
  MySAMLProvider:
    Type: AWS::IAM::SAMLProvider
    Properties:
      Name: MyIdP
      SamlMetadataDocument: |

📋 メタデータXMLの中身を理解しよう

📄 メタデータに含まれる情報

1. エンティティID
IdPを識別する一意のID
例： https://idp.example.com/

2. SSO URL
ログイン時のリダイレクト先
例： https://idp.example.com/sso

3. 署名証明書（X.509）
SAMLアサーションの署名を検証する公開鍵
<X509Certificate>...</X509Certificate>

4. NameID形式
ユーザー識別子の形式
例： urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress

🔍 証明書ローテーション時のポイント

✅ 複数の証明書が含まれる場合
メタデータには複数の <X509Certificate> を含められます。
新旧両方の証明書が含まれていればOK！

✅ AWSの動作
AWSは登録された全ての証明書で署名検証を試みます。
どれか一つでも一致すれば認証成功！

⚠️ 注意点
• メタデータのサイズ上限：10MB
• 証明書の形式：Base64エンコードされたDER形式
• XMLの構文エラーに注意

🔍 証明書有効期限チェックスクリプト（Python + Lambda） 
import boto3
import xml.etree.ElementTree as ET
from datetime import datetime, timedelta
from cryptography import x509

def check_saml_certificate_expiry(event, context):
    iam = boto3.client('iam')
    sns = boto3.client('sns')
    
    # IAM IDプロバイダーの一覧を取得
    providers = iam.list_saml_providers()['SAMLProviderList']
    
    for provider in providers:
        arn = provider['Arn']
        metadata = iam.get_saml_provider(SAMLProviderArn=arn)
        
        # メタデータから証明書を抽出
        root = ET.fromstring(metadata['SAMLMetadataDocument'])
        certs = root.findall('.//{http://www.w3.org/2000/09/xmldsig#}X509Certificate')
        
        for cert_elem in certs:
            cert_data = cert_elem.text
            cert = x509.load_pem_x509_certificate(
                f"-----BEGIN CERTIFICATE-----\n{cert_data}\n-----END CERTIFICATE-----".encode()
            )
            
            # 有効期限を確認（60日前にアラート）
            days_until_expiry = (cert.not_valid_after - datetime.utcnow()).days
            
            if days_until_expiry < 60:
                sns.publish(
                    TopicArn='arn:aws:sns:ap-northeast-1:123456789012:alerts',
                    Subject=f'⚠️ SAML証明書が{days_until_expiry}日後に期限切れ',
                    Message=f'Provider: {arn}\n期限: {cert.not_valid_after}'
                )

❓ よくある質問（FAQ）

🤔 証明書の有効期限が切れたらどうなる？
全てのSAML認証が失敗します。 IdPは期限切れの証明書で署名を続けますが、その署名は無効とみなされます。結果として、AWSにログインできなくなり、業務に大きな影響が出ます。必ず期限切れ前に更新しましょう。
🤔 複数のAWSアカウントで同じIdPを使っている場合は？
全てのAWSアカウントで更新が必要です。 証明書ローテーションの際は、全アカウントのIAM IDプロバイダーを更新してから、IdP側で新しい証明書に切り替えてください。AWS Organizationsを使っている場合は、StackSetsで一括更新することも可能です。
🤔 IdP側で証明書を自動ローテーションする設定がある場合は？
要注意です！ IdPの自動ローテーション機能は便利ですが、AWS側のIAM IDプロバイダーも自動で更新されるわけではありません。IdPの自動ローテーション設定と連動して、AWSのメタデータも更新する仕組みを構築するか、IdPの自動ローテーションを無効にして手動管理することを推奨します。
🤔 更新後に一部のユーザーだけログインできない場合は？
以下を確認してください：
• ブラウザキャッシュ ：古いSAMLレスポンスがキャッシュされている可能性。シークレットウィンドウで試す
• IAMロールの信頼ポリシー ：特定のロールだけ問題がある場合は、そのロールの信頼ポリシーを確認
• CloudTrailログ ： AssumeRoleWithSAML イベントでエラー内容を確認
🤔 ダウンタイムなしで更新できる？
はい、正しい手順なら可能です。 ポイントは「新旧両方の証明書が有効な期間」を作ることです。AWS側で新しい証明書を認識させてから、IdP側で署名を切り替えれば、ユーザーに影響なく更新できます。本ガイドの手順に従えば、ダウンタイムゼロで更新できます。
⚠️ 絶対に守るべき重要ルール
1. 順番を守る： 必ず「AWS側を先に更新」→「IdP側で切り替え」の順番で！

2. 古い証明書は急いで消さない： 動作確認が完了するまで古い証明書は残しておく

3. 複数アカウントは全て更新： 一つでも漏れると、そのアカウントへのアクセスが不能に

4. 本番前にテスト： 可能であれば、開発/検証環境で先に試す
💡 ベストプラクティス Tips
1. 証明書の有効期間を長めに設定：
可能であれば3年以上の有効期間を設定。ローテーション頻度を減らせる。

2. カレンダーリマインダーを設定：
証明書発行時に、有効期限の90日前にリマインダーを設定しておく。

3. Infrastructure as Codeで管理：
TerraformやCloudFormationでIAM IDプロバイダーを管理。変更履歴が追跡可能に。

4. 複数人でのダブルチェック：
重要な変更は二人以上で確認。手順の見落としを防止。

5. ロールバック計画を常に用意：
古いメタデータのバックアップを取り、いつでも戻せる状態にしておく。
